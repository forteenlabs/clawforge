# Build 0.0.6 — State

## Status

**Active Discovery**

## Purpose

This build defines ClawForge's first executable capability: observing and communicating the current state of a ClawForge repository before interpretation, evaluation, or modification begins.

Build 0.0.4 established that Orientation must precede responsible participation.

Build 0.0.5 established the Integrity process that governs meaningful changes to ClawForge.

Both capabilities depend upon reliable evidence about the repository being examined.

Build 0.0.6 therefore explores how ClawForge establishes observable repository State and presents that evidence honestly before further reasoning or action occurs.

## Scope

This build applies to the observable state of a ClawForge repository.

The initial capability will examine the local repository in which it is executed, including:

* repository location
* current Git branch
* current commit
* working-tree status
* tracked modifications
* untracked files
* locally recorded remote relationship
* presence of required ClawForge artifacts
* declared current and completed builds
* evidence supporting each reported state claim
* missing, unavailable, stale, or contradictory evidence

Remote repository state is related but distinct.

A remote comparison requires an explicit refresh of remote information. ClawForge must not claim that a local repository matches GitHub merely because locally cached tracking information appears synchronized.

This build does not verify VS Code or another editor. VS Code may display and modify the repository, but State evaluates the repository itself.

## Core Question

> How does ClawForge establish and communicate the observable state of a repository before a human, intelligence, or implementation attempts to reason about or change it?

## Emerging Principle

ClawForge must observe state before interpreting it, and preserve evidence before claiming understanding.

## State Boundaries

### Local State

Local State describes the repository and working files present on the machine where the State capability is executed.

Local State must be available without network access and must not modify the repository.

### Remote State

Remote State describes the relationship between the local repository and a remote repository such as GitHub.

A reliable Remote State comparison requires an explicit refresh of remote information.

ClawForge must distinguish:

* synchronized
* locally ahead
* locally behind
* diverged
* unavailable
* not refreshed

### Known Good State

A clean Git working tree does not by itself establish Known Good State.

Known Good State is a governed historical designation produced through ClawForge's accepted process.

The State capability may report evidence associated with a declared Known Good State, but it must not manufacture that designation from technical cleanliness alone.

## Initial Capability

The first executable State capability should:

1. locate the repository
2. observe local repository evidence
3. distinguish current evidence from cached or unavailable evidence
4. identify missing or contradictory state information
5. produce a deterministic and understandable report
6. exit without modifying repository contents

## Initial Flow

```text
REPOSITORY
    |
    v
OBSERVE LOCAL STATE
    |
    v
STATE EVIDENCE
    |
    v
OPTIONAL REMOTE REFRESH
    |
    v
LOCAL / REMOTE RELATIONSHIP
    |
    v
STATE REPORT
    |
    v
ORIENTATION
```

## Out of Scope

This build does not yet:

* modify repository files
* repair discovered discrepancies
* evaluate proposed changes
* issue an Integrity `HOLD` or `PROCEED`
* perform complete Orientation
* certify external agents or systems
* verify the correctness of VS Code or another editor
* claim semantic correctness from Git status alone
* operate autonomously

## Initial Validation Scenarios

### Scenario 1 — Clean Local Repository

The repository is on a recognized branch and commit with no tracked or untracked changes.

### Scenario 2 — Tracked Modification

One or more tracked files differ from the current commit.

### Scenario 3 — Untracked File

The repository contains one or more files not tracked by Git.

### Scenario 4 — Local and Remote Synchronized

Remote information has been explicitly refreshed and the local branch matches its remote tracking branch.

### Scenario 5 — Stale Remote Knowledge

Remote information has not been refreshed during the State process.

ClawForge must not report current remote synchronization as verified.

### Scenario 6 — Local Ahead or Behind

The local and remote branches do not point to the same history position.

### Scenario 7 — Missing Required Artifact

A required ClawForge document or directory cannot be found.

### Scenario 8 — Contradictory Build State

Authoritative records disagree about the active build, completed build, or Known Good State.

### Scenario 9 — Outside a ClawForge Repository

The State capability is executed where no valid ClawForge repository can be identified.

### Scenario 10 — Git Unavailable

Git evidence cannot be collected.

The State report must distinguish unavailable evidence from a clean or valid result.

## Initial Reference Implementation

Build 0.0.6 proposes Python as ClawForge's first replaceable reference implementation.

Python is an implementation choice, not part of ClawForge's identity.

The canonical command interface will be:

```text
clawforge
```

The initial State capability will eventually be invoked as:

```text
clawforge state
```

During development, the equivalent entry point may be:

```text
python -m clawforge state
```

ClawForge may provide `cf` as an optional convenience alias.

The alias must route to the same command behavior as `clawforge`, must not be required for operation, and may be unavailable where it conflicts with another command.

This proposed architectural decision is preserved in `docs/decisions/ADR-0002.md`.

## Architectural Boundary

State gathers and reports observable evidence.

Orientation uses that evidence to establish sufficient understanding.

Integrity governs whether meaningful change may proceed.

State must support those later capabilities without absorbing their authority.
